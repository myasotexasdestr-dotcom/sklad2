# Бекенд «Мясо з Техасу»

Express + SQLite. Зберігає весь спільний стан (локації, склади, товари, замовлення, штат, графік,
рейтинги тощо) в одній таблиці в базі й роздає його всім пристроям через `/api/state` — саме це і
дає синхронізацію замість локального `localStorage`.

Той самий сервіс роздає і сам клієнт (`public/sklad.html`) як звичайну сторінку — тобто це один
деплой, одна https-адреса, яку і вставляєте в BotFather.

## Локальний запуск (перевірити перед деплоєм)

```bash
cd server
npm install
npm start
```

Відкрити http://localhost:3000 у браузері. Перший вхід — власник, пін **0000**. Одразу зайдіть у
Налаштування → Співробітники → Редагувати і поміняйте цей пін на щось непередбачуване (він відкриває
повний доступ).

## Як це працює

- Увесь бізнес-стан лежить в `data/app.db` (SQLite, один рядок таблиці `app_state`) — файл
  створюється сам при першому запуску.
- Пін звіряється на сервері (`POST /api/auth/login`), не на клієнті — видає токен сесії.
- Клієнт тримає токен у `localStorage` цього пристрою (не в спільних даних) і шле його в заголовку
  `Authorization: Bearer <token>` у кожному запиті.
- `GET /api/state` — забрати поточні спільні дані; `PUT /api/state` — зберегти, з номером версії:
  якщо хтось інший встиг зберегти першим, повертається `409` з актуальними даними, і клієнт сам
  підтягує свіже й повідомляє користувача, замість того щоб мовчки затерти чужі зміни.
- Клієнт ще й опитує сервер кожні 5 секунд (`GET /api/state`), тож зміни з іншого пристрою
  з'являються на екрані без перезавантаження сторінки.

## Важливо розуміти

- **Пін-код — це весь захист.** Він всього 4-6 цифр, а сервер буде доступний з інтернету (Telegram
  вимагає https-адресу). Є базовий rate-limit на спроби логіну (20 спроб / 15 хв на IP), але для
  реального бізнесу вартувало б: довші піни, або перевірка `initData` від Telegram WebApp (підтвердить,
  що запит справді прийшов із Telegram-клієнта конкретного користувача) — цього тут поки немає,
  можна додати окремо.
- **Дані одного пристрою = дані всіх.** Сервер віддає весь стан будь-якому залогіненому
  співробітнику — рольові обмеження (що касир не бачить собівартість тощо) застосовуються, як і
  раніше, на клієнті, не на сервері. Для довіреної невеликої команди це прийнятний компроміс (так
  само було й у локальній версії), але це не повноцінна серверна авторизація по ролях.
- **SQLite-файл повинен пережити передеплой.** Дивись інструкцію з деплою в чаті — на безкоштовних
  тарифах багатьох хостингів диск ефемерний і файл БД зникає при кожному рестарті/релізі, якщо не
  підключити постійний диск (volume).

## Структура

```
server/
  server.js       — весь бекенд (auth, /api/state, роздача public/ як статики)
  package.json
  public/
    sklad.html    — клієнт, той самий, що й раніше, але з сервером замість localStorage
  data/
    app.db        — створюється автоматично при першому запуску (не в git)
```
